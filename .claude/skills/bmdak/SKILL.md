# bmdak core workflow

사내 MDaK 지식에 근거가 필요한 작업은 이 절차를 따른다. 이 문서와 설치된
`bmdak <command> --help`가 plugin stub이나 저장소 문서보다 우선한다.

## 준비와 인증

레거시 모델 호출과 폐점한 플러그인은 사용하지 않습니다. `bmdak init`은 출처가 확인된
옛 상점 등록·설치본·캐시·갱신 후크를 백업 없이 제거합니다. 명확한 옛 CodeB 호출 지시와
직접 실행 후크도 비활성화합니다. 기존 기능과 bmdak 대체 경로를
프로젝트의 `bmdak-legacy-removal.md` 원장에 누적한 다음 프로젝트 규칙·스킬을 초기화합니다.
제거 범위는 폐기가 확인된 대상입니다. 이름·문자열 일치 후보와 정상 기능은 자동 제거하지 않습니다.
남은 후보·미검사 항목은 `bmdak legacy scan`으로 확인하고 현행 기능 사용과 병행해
정리합니다. 확정된 레거시가 남으면 제거 완료로 보고하지 않습니다. 남은 정리를 이유로
온보딩·현행 기능 사용을 중단하거나 옛 기능을 다시 허용하지 않습니다.
초기화 성공과 레거시 정리 완료는 구분합니다. CodeB의 `chat`, `embed`,
`search`, `explore`, `braintrust`, `fusion`, `image`, `tts`, `sfx`, `sts`, `isolate`,
`video`, `cg` 호출은 현행 MDaK 방법론으로 전환합니다. 로그인·Pages·목록·예산 조회는
유지합니다. 마켓 등록 ID와 설치 경로로 출처를 구분하며, 현행 `punkcode-plugins`·
`baker-marketplace`·`bagel-marketplace` 설치본은 같은 이름이어도 보존합니다.
예외로 폐기가 확정된 `game-lens`·`game-eye`는 출처·사용 여부와 관계없이 제거합니다.
`bakery-plugins`를 재등록·재설치·재활성화하거나 옛 설치본·갱신 후크를
복원해 사용하지 않습니다. 옛 문서·도움말에 명령이 남아 있거나 현재 바이너리가 받아도
위 CodeB 모델 명령은 호출하지 않습니다. MDaK 조회나 현행 API 호출이 실패해도 옛
명령·플러그인으로 우회하지 않고 실패 원인을 해결합니다.
자동 정리 범위 밖의 사용자 문서·혼합 스킬은 대상과 변경안을 제시하고 승인된 것만 정리합니다.
`legacy plan`으로 변경안을 만들고 사용자 승인 후 출력된 해시로 `legacy apply`를
실행합니다. 혼합 스킬은 정상 기능을 남긴 수정본을 준비합니다. 금지문·과거 기록은
실제 호출과 구분해 `--not-active --reason`으로 근거를 남깁니다. 제거한 내용의 백업과
복구 기능은 제공하지 않습니다. 보고서에는 실행 원문 대신 기존 기능과 대체 경로를 남깁니다.
기존 세션의 기억은 남으므로 새 세션에서 발견 목록과 실제 호출 경로를 확인합니다.

1. bmdak 명령은 앞에 셸 준비 코드를 붙이지 않고 `bmdak search …`처럼 그대로 실행한다.
   설치기가 설치 폴더를 로그인 셸의 PATH에 등록하므로 새 셸에서도 찾는다. `bmdak`을 찾지
   못하면 사용자에게 bmdak 재설치를 요청한다. 재설치 뒤에도 찾지 못하면 실행 중인 에이전트가
   옛 PATH를 물려받고 있으므로 사용자에게 에이전트 앱이나 세션 재시작을 요청한다.
   셸에 남은 `MDAK_RAG_SERVER` 때문에 prod 외 서버 접근 거부 오류가 나면 셸 준비 코드로
   우회하지 않고, 사용자에게 셸 설정에서 그 변수를 지우도록 요청한다.
   명시 서비스 호출은 승인된 --server·--token-file을 따른다.
   bmdak는 harness가 셸에 물려주는 대화 id
   (`CLAUDE_CODE_SESSION_ID`·`CODEX_THREAD_ID`)를 해시한 세션 라벨로 search·doc·get-section
   호출을 서버 telemetry에 묶는다 — 값을 읽거나 출력하지 않으며, `MDAK_RAG_NO_SESSION=1`로 끈다.
2. 프로젝트에 bmdak 규칙과 skill이 아직 없으면 프로젝트 폴더에서 `bmdak init`을 한 번
   실행한다. CLI 갱신 후 기존 프로젝트 스킬도 갱신하려면 같은 폴더에서 다시 실행한다.
   자세한 갱신 범위는 `bmdak help init`으로 확인한다. HOME에서는 실행하지 않는다.
3. `bmdak health`로 연결과 색인 상태를 확인한다. 공개 health 성공은 인증 성공이 아니다.
   인증은 원래 하려던 search·doc·get-section 조회의 성공으로 확인한다.
4. 개인 자격이 없거나 만료됐거나 개인 호출이 401이면 사용자에게 `codeb login`을 요청한다.
   사용자가 로그인을 마친 뒤 원래 명령을 한 번만 재시도한다. 같은 자격으로 반복하지 않는다.
   명시 서비스 토큰 호출의 401은 대상 prod·dev와 승인된 --token-file을 확인하고,
   필요한 자격 갱신 후 재시도한다. 개인 로그인으로 서비스 자격을 대체하지 않는다.
5. 에이전트가 자격 파일·토큰 원문을 열람하거나 출력하거나 대화·로그·설정에 복사하지 않는다.
   기존 도구와 현행 문서에 따라 작성한 호출 코드가 자격을 프로세스 내부에서 읽고,
   지정된 서비스 인증에 사용하는 것은 정상 경로다. 내부 인증 사용을 원문 열람으로 오해해
   도구 연결을 중단하지 않는다. 인증 사용과 유료 호출 승인은 별개다. 과금 호출에는
   사용자의 명시적 허락과 해당 도구·호스트의 정책을 따른다.
6. 해당 도구의 인증은 정상인데 생성이 실패하면 현행 도구·요청 형식·호출 경로를 확인한다.
   bmdak 조회 성공이 다른 생성 도구의 인증·권한까지 보장하지는 않는다.
   인증 실패 근거 없이 다시 로그인시키거나 토큰 원문을 확인하려 하지 않는다.

## 접속 실패와 복구

- DNS 이름 해석 오류만으로 서버 장애나 샌드박스 제한을 확정하지 않는다.
  서버 주소·DNS·VPN/프록시와 실행 환경의 네트워크 정책을 확인한다.
- CODEX_SANDBOX_NETWORK_DISABLED=1은 네트워크 제한 신호이고,
  CODEX_SANDBOX=seatbelt는 샌드박스 실행 신호다. 현재 실패의 직접 원인을
  증명하지 않으며, 신호가 없어도 네트워크 제한이 없다고 단정하지 않는다.
- Codex에서 제한이 의심되면 현재 호스트의 정책과 승인 기능을 먼저 확인한다.
  허용된 승인 절차가 있을 때만 원래 실패 명령을 같은 대상·인자로 한 번 재시도한다.
  실행 도구가 지원·허용하는 sandbox_permissions="require_escalated"가 한 예이며,
  이는 bmdak 옵션이 아니다. 일반 터미널·Claude에서는 해당 호스트의 절차를 따른다.
- 승인 거절·기능 부재·정책 금지이면 그 상태를 보고한다. 거절 뒤 우회하거나
  같은 조건으로 반복하지 않는다. 승인 후에도 재시도 실패와 성공을 구분해 보고한다.
  CLI나 에이전트가 사용자·조직 설정을 자동 변경하거나 자체적으로 제한을 해제하지 않는다.
- 공개 health 성공은 인증이 필요한 문서 조회 성공을 보장하지 않는다.
  원래 실패한 조회까지 성공했는지 확인한다. DNS 실패를 지식 부재로 보고하지 않는다.
- TLS 인증서 오류는 CA 안내를, HTTP 401/403은 인증·권한 안내를 따른다.
  서버 오류의 retryable·action·Retry-After 계약을 유지한다.

## 첫 온보딩 — init 직후 첫 대화

프로젝트가 방금 init 됐거나 사용자가 시작을 물으면(예: "뭐부터 할까"), 아래를 한 번
수행한다. 목록을 외우거나 하드코딩하지 않는다 — 조회 결과가 정본이다.

1. 조회는 **한 번의 셸 호출**로 끝낸다 — 세 명령을 이어 실행한다:
   `bmdak get-section 'mentor:bakery-domain-map#c0' && bmdak doc mentor:bakery-tool-map && bmdak list --limit 500`
   (list 기본 한도는 잘린다 — 반드시 `--limit 500`. health 를 따로 확인할 필요 없다 —
   이 조회의 실패가 곧 그 신호다.)
2. 도메인 브리핑은 **도메인 지도 문서의 한 줄들을 그대로** 쓴다. `list` 는 대조용이다 —
   지도에 없는 `doc_id` 접두사가 보이면 그 도메인은 "신규(설명 미등재)"로 한 줄
   브리핑한다. 지도 문서를 못 찾으면(미색인) `list` 접두사만으로 도메인당 한 줄씩
   브리핑한다. 어느 쪽이든 문서 단위 나열은 하지 않는다.
3. 도구 지도는 **절 제목(heading_path)만으로** repo 형태 도구를 **repo당 한 줄
   (최대 두 줄)**로 브리핑한다 — 지도는 절 하나가 도구 하나다. 온보딩에서 도구
   절 본문을 읽지 않는다. mdak 밖, clone해 쓰는 실행물임을 밝힌다(클론 위치 규약은
   지도의 해당 절이 정본).
4. 브리핑 끝에 반드시 이렇게 묻고 멈춘다: **"어떤 게임을 만들까요? 기획 방향성은
   어떻게 할까요?"** — 기획을 대신 정하지 않는다. 브리핑은 대화 텍스트로만 한다 —
   파일·HTML 산출물을 만들지 않는다.
5. 사용자가 답하면 mentor 도메인 지식을 조회해 기획 셋업을 이어간다.

## 근거 검색

1. `bmdak search "<질문>"`을 실행한다. 기본 `k=10`을 유지하고 반환된 모든 hit의
   `excerpt`를 검토한다. `-k`는 서버 상한 100까지 지정할 수 있다. 100보다 크게
   지정해도 서버는 최대 100건을 반환한다. hit 순서로 합격을 판정하지 않는다. 반환된
   hit는 `k`와 관계없이 모두 검토 대상이다.
2. 관련 hit마다 `bmdak doc '<doc_id>'`로 문서 구조와 섹션 목록을 확인한다.
3. 과업의 각 요구사항에 필요한 섹션을
   `bmdak get-section '<section_id>'`으로 읽는다. 여러 절·문서를 이어 읽을 때는 셸에서
   bmdak를 반복하지 말고 `bmdak read '<id>' '<id>' …`(최대 20개)로 한 번에 읽는다 —
   결과는 입력 순서대로 1:1이고 항목별 `status`로 성공·없음·실패를 구분한다.
4. 관련 문서 그래프가 필요하면 `bmdak related-to '<doc_id>'`를 사용한다 — `--depth`는 홉 수
   (1~5, 기본 1)이며 넓히려면 2까지만 쓴다. 5는 잘 연결된 뿌리에서 코퍼스 대부분을 id로 쏟아내
   `list`와 다를 게 없다. 응답은 간선(id 쌍)뿐이라 이웃은 `doc`/`get-section`으로 연다.
   메타데이터 목록이 필요하면 `bmdak list`를 사용한다. 명령별 안내는 `bmdak help <명령>`.
5. 근거가 부족하면 검색어를 도메인과 의도가 드러나게 구체화해 다시 기본 `k=10`으로
   검색한다. 끝내 근거가 없으면 추측하지 않고 지식 부재로 보고한다.

## 원본 증거물 열기

- `_evidence.coordinates`는 `bmdak source '<section_id>'`(문서 id·`owner/repo:경로`도 된다)로 연다.
  사용자의 `gh` 인증으로 열어 `local_path`에 두고, 못 연 원인은 `status`로 준다. `ok`·`directory`만
  열린 것이다. `no_access`는 이 계정에 저장소가 보이지 않는다는 뜻이고(비공개 저장소는 권한이 없어도
  404로 가려진다), `not_found`는 좌표가 가리키는 경로가 저장소 이력에 없다는 뜻이다. 열지 못한 좌표를
  읽은 것으로 보고하지 않는다.
- 모든 `found=true` get-section 응답에는 `source_repo`·`source_path`·`_resolve`가 실린다.
- Markdown 상대 링크는 `source_path`가 가리키는 파일의 디렉터리를 기준으로 정규화한다.
- 문서가 repo-root 경로로 명시한 코드 스팬(`samples/…`·`tools/…`·`data/…`)은
  `source_repo` 루트 기준으로 정규화한다.
- 좌표가 아닌 본문 링크를 직접 정규화했다면 `gh api repos/<source_repo>/contents/<정규화경로>`로 연다. 정규화 결과가
  원본 repo 밖이면 열지 않는다.
- 외부 스킴 URL·앵커(`#…`)·절대 경로(`/…`)는 원본 repo 상대 경로로 해석하지 않는다.
- `source_repo`·`source_path`가 null이면 `sources.yml`이 없거나 잘못됐거나 문서가 커버리지
  밖이라는 뜻이다. 이 경우에도 get-section은 fail-open으로 200을 유지한다.
- `search` hit·`doc.sections[]`·`get-section`에 `_evidence`가 있으면 `coordinates`의 모든
  원본을 구현 완료 판정 전에 반드시 연다. 열람한 내용을 설계에 채택할지는 소비 에이전트가
  판단한다.
- `_evidence.unresolved_links`는 내부 경로 신호는 있으나 접근 좌표를 만들지 못했다는 뜻이다.
  존재를 보고하되 접근 불가능한 대상을 열었다고 간주하지 않는다.

## 결과 판정

- 지식 조회 결과는 JSON이다. 명령이 비정상 종료하면 성공으로 간주하지 않는다.
- 오류 JSON은 `code`·`cause`·`action`·`retryable`·`retry_after_seconds`를 따른다.
  `retryable=false`이면 같은 요청을 반복하지 않는다. `true`여도 `action`에 따라
  기다리며 즉시 반복 호출하지 않는다. `request_id`가 있으면 지속 장애 보고에 포함한다.
- 리뷰·시험에서 검색 도달은 기대 절이 기본 10건 안에 있는지로 판정한다.
- hit 순서(순위)·`score`·`bm25`·`vector`는 진단값이지 정답 판정이 아니다.
  excerpt와 섹션 본문을 직접 읽어 판단한다.
- 열람 응답에 `_corpus_changed`가 있으면 그 검색 이후 코퍼스가 바뀌었거나 확인할 수 없다는 뜻이다. `#c` 주소가
  다른 절을 가리킬 수 있으므로 같은 질의로 search를 다시 실행하고 새 id로 읽는다.
- 답변 근거에는 가능한 범위에서 `doc_id`·`section_id`·`heading_path`·`file_path`를
  남긴다. 원본 증거물은 위 `source_repo`·`source_path`·`_resolve` 절차를 따른다.
- 정확한 플래그와 현재 응답 계약은 `bmdak --help`와 각 하위 명령의 `--help`로 확인한다.
